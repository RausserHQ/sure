# Liability code, fork changes, and upstream evidence

Research for [Assess current liability code and the fork and upstream fixes](https://github.com/RausserHQ/sure/issues/21) in the new [Wayfinder: plan end-to-end liability correctness from main](https://github.com/RausserHQ/sure/issues/19). Checked 2026-09-26 (Pacific time).

## Scope and conclusion

The implementation baseline is [main `437c317606497d713a6683f8d8c9a64a17602efd`][main]. The comparison is [production `aab841bf32492220e24ee7828c648da8c085065f`][production]. This report does not choose an upgrade, backport, reporting policy, schema, or repair plan. Archived research supplied navigation only; material conclusions below were checked against source, PR diffs, comments, and git ancestry.

**Current main has useful balance and transfer machinery, but it does not establish end-to-end liability correctness.** Its Loan balance calculator applies whole normalized activity amounts; it does not establish the principal component of those amounts. Import classification, persisted transfer relationships, budget reporting, and public read classifications can disagree. OtherLiability has a separate, explicit transaction-ignoring balance behavior. [Balance calculation][base-calculator], [import classification][adapter], [transaction kinds][transaction], [report classification][report-query].

The production patches supply useful synthetic requirements and some lifecycle protections. Their description regexes, blanket exclusion of `loan_payment`, and treatment of unknown credits are application assumptions requiring a new decision. None proves the meaning of a particular provider balance or transaction. The newer upstream candidates include narrowly relevant fixes, but most remain open; one reporting PR's current code materially differs from its title. [Correct liability and cashflow semantics][fork8], [Harden SimpleFIN payroll, principal, refund, and transfer semantics][fork10], [Current investment and loan reporting proposal][u3609-code].

**Evidence limits:** this was static research. No application tests, migrations, syncs, production commands, or household-data investigation ran. Existing test source is mapped below; historical CI statements are author reports, not this research's validation. A separate unchanged-main suite result does not prove the new accounting requirements. Protocol and household authority questions belong to the sibling evidence ticket.

## Current code and test map

### Provider observations and normalization

`SimplefinAccount` retains the latest raw payload, `current_balance`, `available_balance`, and parsed `balance_date`. The regular processor picks current balance unless it is actually nil, so an explicit zero survives; then it writes `Account.balance`, `cash_balance`, and currency. The minimal/discovery importer also stores the provider timestamp and writes through `ProviderImportAdapter#update_balance`. Neither write path calls `CurrentBalanceManager`. These are latest snapshots, not an append-only observation history. [Snapshot fields][simplefin-account], [regular processor][simplefin-processor], [minimal importer][simplefin-importer], [balance adapter][adapter-balance].

| Type | Regular and minimal SimpleFIN balance handling on fixed main | Historical movement handling |
| --- | --- | --- |
| Loan | Both use `abs(observed)` and bypass the credit-card analyzer. This forces nonnegative debt; it does not preserve a negative loan credit or prove the quantity is principal. | `:non_cash`; eligible activity changes non-cash balance. Positive normalized entry amounts increase debt going forward; negative amounts reduce it. |
| CreditCard | Explicit `credit`/`debt` override wins; otherwise analyzer, then sign fallback. Current balance wins over available balance, including zero. | `:cash`; activity changes debt with liability direction, opposite asset direction. |
| OtherLiability | Not included in the linked `CreditCard`/`Loan` normalization set. An explicitly linked type outranks mapper inference. | `:non_cash`, but lacks Loan's activity branch: transactions remain recorded and are ignored for historical balance movement; valuations can reset balance. |

Sources: [balance-type mapping][account-type], [normalizer][simplefin-processor], [minimal normalizer][simplefin-importer], [calculator][base-calculator], [forward tests][forward-tests].

There is **no current regular/minimal Loan sign discrepancy**: both use `abs`. Upstream [Fix SimpleFIN balances-only liability signs](https://github.com/we-promise/sure/pull/3187) fixed the earlier minimal path that calculated normalization but wrote the raw balance; its reviewed revision also added Loan bypass, explicit-zero handling, and linked-type precedence. That merge is in both pinned branches. Credit-card override [SimpleFIN: add a credit card balance sign override](https://github.com/we-promise/sure/pull/3243) extends both paths on main and is absent from production. [Minimal-path tests][minimal-tests], [sign-override migration][override-migration].

The credit-card analyzer is an inference, not independent evidence. It uses a configurable recent window, minimum counts, a sticky cached result, and raw-payload fallback. Its preferred query is `account.entries.where(date >= ...)`: it does not restrict that signal to Transactions or exclude pending, split parents, or valuations. The balance calculator has different filters. Therefore the analyzer's label must not be read as proof of the account's economic state. [Analyzer source][analyzer].

`SimplefinEntry::Processor` negates every provider transaction amount, supplies no semantic `kind`, preserves payee/memo/description/provider `extra`, and writes a true/false pending flag. Its date preference uses the provider account-type string: credit/card/loan/mortgage prefers transacted date; others prefer posted date. Missing posted alone is not pending; explicit pending or posted zero plus a positive transacted timestamp is. This normalization is separate from the absolute account-balance normalization. [Entry processor][simplefin-entry], [processor tests][entry-tests].

The shared adapter classifies any negative Loan amount as `loan_payment`, ahead of an explicit provider kind fallback. On main it no longer classifies every negative CreditCard entry as `cc_payment`; upstream [Credit-card credit classification fix](https://github.com/we-promise/sure/pull/3062) removed that branch and made Brex negative card `COLLECTION` explicit. A new unpaired SimpleFIN card credit therefore normally remains `standard`, not a proven refund or payment. Positive Loan activity normally remains standard too. [Adapter][adapter], [FIX: Refunds or credits incorrectly recorded as cc_payment](https://github.com/we-promise/sure/pull/3062).

### Current anchors, reconciliation, and history

Linked accounts materialize in reverse; manual accounts materialize forward. The cache converts entries into account currency, excludes pending Transactions and split parents, and returns only Transactions/Trades as activity. Valuations are fetched separately and reset balances. `excluded` is a report/import-protection flag, not a universal instruction to remove balance effects: the cache does not filter all excluded entries. Missing FX entries are omitted with a diagnostic. [Sync order][account-syncer], [cache][sync-cache], [entry scopes][entry-scopes].

Loan's non-cash calculation uses the sum of eligible activity amounts without consulting `Transaction.kind` or a `Transfer` row. Its transaction flow columns record negative and positive transaction totals. Reclassifying payroll, interest, or proceeds alone cannot change that numerical balance effect. The test fixture explicitly assumes the whole payment is principal; that assertion tests today's behavior, not actual principal knowledge. The UI nevertheless labels the Loan chart and reconciliation quantities as principal. [Calculator][base-calculator], [Loan tests][forward-tests], [chart labels][chart], [reconciliation labels][reconciliation-ui].

**Fallback matters:** with no current-anchor valuation, `current_anchor_balance` resolves to cached `account.balance`, and `current_anchor_date` resolves to `Date.current`. Thus a SimpleFIN snapshot can anchor reverse history indirectly. It is incorrect to conclude that SimpleFIN snapshots cannot anchor history. However, this path ignores provider `balance_date` and does not rotate prior snapshots into valuation waypoints. If a current-anchor valuation already exists, its amount/date take precedence over the newly updated cache; stale-anchor disagreement is therefore possible. [Current manager][current-manager], [reverse calculator][reverse], [fallback tests][anchor-tests].

When called by a provider/workflow using `set_current_balance`, the shared manager rotates a prior-day current valuation into a reconciliation and creates today's anchor; same-day updates replace the same anchor. Reverse calculation treats a reconciliation as end-of-day value and derives that day's start from its activity. It forces an opening anchor on its date and records the boundary difference on the next day as explicit cash/non-cash adjustments. Those fields expose a discrepancy; they do not identify missing principal, interest, transactions, or a bad observation. [Manager][current-manager], [reverse implementation][reverse], [materialization test][materializer-tests].

A user reconciliation records an absolute value, not income or expense. A linked reverse materialization does not update the cached displayed account balance (`Materializer` does that only for forward runs). That distinction explains why a correction may affect history without changing the linked account's headline value. The open linked-valuation report is consistent with this source path, but this research did not reproduce a UI case. [Reconciliation manager][reconciliation-manager], [materializer][materializer], [Bug: Valuations (reconciliation entries) don't update the displayed balance on linked/synced accounts](https://github.com/we-promise/sure/issues/3385).

### Transfer lifecycle and reporting

| Stage | Observed behavior | Consequence to test in a new plan |
| --- | --- | --- |
| Import | Same source/external ID is updated; pending reconciliation and protected-entry rules apply. Loan negative amounts can be stamped `loan_payment` on every unprotected import. | Reimport is not semantically idempotent after another writer changes kind. |
| Automatic match | Pairs different same-family accounts by amount/date; four-day window; cross-currency automatic matching limited to linked accounts with configurable tolerance. Marks inflow `funds_movement` and outflow from destination type. | Equal/opposite amount is a candidate heuristic, not evidence that payroll/refunds are transfers. Current main has no fork payroll/refund guard. |
| Destination type | Loan outflow becomes `loan_payment`; CreditCard and other liabilities become `cc_payment`; investment/crypto becomes contribution. | A Loan destination does not establish a principal-only payment. OtherLiability gets payment presentation although its calculator ignores the transaction. |
| Repeat import | Adapter does not guard kind assignment with an existing transfer relationship. Matcher skips already-paired entries. | A Loan inflow may return to `loan_payment`, making both legs expense in income-statement queries. |
| Reject/unmatch | `reject!` records the rejected pair and destroys its Transfer. `destroy!` resets both surviving kinds to `standard`, removes fee rows, and clears retained entry idempotency keys. | Independent meaning is lost; rejection blocks rematching that pair but does not establish a new economic classification. |
| Manual create and split | Creator makes a confirmed pair, with optional separate standard fee Transactions. `splittable?` rejects transfer kinds, pending, excluded, or already split entries. | A known fee-component precedent exists; automatic mortgage component inference does not. Full payment splitting crosses existing transfer restrictions. |

Sources: [adapter][adapter], [automatic matcher][matcher], [Transfer lifecycle][transfer], [creator][creator], [split predicate][splittable]. Account post-sync and family post-sync both match transfers; family rules run afterward and are another classification writer. [Account sync][account-syncer], [family sync][family-syncer].

The transfer relationship and `Transaction#transfer?` are different: the latter checks a kind list and may be true without any pair; `transaction.transfer` resolves the actual inflow/outflow association. Current reporting filters mostly use kind. An issue describing a prior persisted-Transfer reporting implementation is historical evidence; the fixed main's query source is authoritative for today's behavior. [Kinds][transaction], [relationship][transferable], [Reporting relies on transaction kind and persisted Transfer as separate authorities](https://github.com/we-promise/sure/issues/2860).

IncomeStatement explicitly makes both `loan_payment` and `investment_contribution` expense and uses their absolute amounts. It excludes funds movement, card payment, one-time entries, pending activity, and selected account scopes. Budgets consume these reports. In contrast, transaction-search income/expense totals exclude all `TRANSFER_KINDS`, including loan payments and investment contributions; pending inclusion depends on the search status filter, and the search starts without the report’s `visible` exclusion scope. Category-level netting can offset ordinary negative credits against purchases, but refunds exceeding purchases can become income. There is no main `refund` kind. [Report query][report-query], [totals query][report-totals], [search][search], [report tests][report-tests].

A synthetic implication: deposit of wages directly into a Loan can reduce its recorded debt while receiving `loan_payment` and being reported as expense; a separately imported interest charge can increase debt and appear as expense while a bundled repayment is also expense. These are deductions from the paths above, not confirmed household events. The distinct balance, income, spending, and budget-reservation effects require explicit acceptance cases.

That is an explicit missing-evidence policy, not a neutral accounting fact. Likewise `loan_payment` exclusion can hide bundled interest because the shared adapter and transfer creator do not guarantee principal-only amounts. Brex's negative non-collection-to-refund assumption remains separate from the tightened SimpleFIN logic in [SimpleFIN semantic hardening](https://github.com/RausserHQ/sure/pull/10). These choices must be accepted, replaced, or narrowed in the new plan. [Production kinds][production-kinds], [production adapter][production-adapter], [production Brex][production-brex].

## Production compatibility constraints and unresolved decisions

The branches are not interchangeable. Production has three extra semantic kinds (`loan_proceeds`, `refund`, `unclassified`), different budget/search/API treatment, description-based amount normalization, restoration metadata, and guards that main lacks. Main has amortization fields/code, card sign overrides, newer protected/pending metadata handling, shared report-query code, FX/matching changes, and transfer idempotency-key cleanup absent from the earlier fork implementation. Both already contain the opening-boundary and minimal-normalization fixes. [Production kinds][production-kinds], [main kinds][transaction], [main adapter][adapter], [main transfer][transfer], [schema][schema].

A later route decision must inventory persisted kinds/metadata and user protections before replacing either implementation, preserve read contracts deliberately, and establish what a recalculation may change in old histories. Cherry-picking by title or copying an old patch wholesale would not account for these interfaces. This is a compatibility constraint, not selection of a migration or automatic data rewrite.

Decisions still required for an implementation-ready plan:

1. What quantity does each accepted provider/user balance establish, at what timestamp, and with what authority when it conflicts with activity or another observation?
2. Which activity amounts are known debt movements versus known principal/interest/fees, and what should remain unknown when a lender supplies a lump sum? Description text and schedule estimates do not settle this.
3. Should OtherLiability represent transaction-driven debt, valuation-driven obligations, or an explicit choice? Its current tests intentionally encode the latter.
4. What are the separate policies for economic income/expense, cash movement, and budget reservation, including principal, bundled interest, refunds, payroll-to-liability, and unclassified credits?
5. What owns semantic classification through import, match, manual override, rule application, rejection, pending settlement and repeat sync? Which user correction survives which writer?
6. How should UI/API/MCP/mobile expose raw amount, meaning, uncertainty and transfer relationship consistently without expanding account access?
7. Which existing observations/anchors are retained, how are stale or intraday readings shown, and how can historical changes be reviewed before any repair? Neither current residual adjustments nor projection math answers causation.
8. Which synthetic acceptance matrix and production compatibility inventory would justify a main-based upgrade or a narrower backport? This research supplies evidence for that choice and does not make it.
